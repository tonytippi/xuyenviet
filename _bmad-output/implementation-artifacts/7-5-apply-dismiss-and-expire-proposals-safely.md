# Story 7.5: Apply, Dismiss, and Expire Proposals Safely

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Trip Project owner,
I want explicit, safe controls for a proposed plan change,
so that AI cannot overwrite my confirmed plan or newer confirmed changes.

## Acceptance Criteria

1. **Atomic owner-confirmed apply with full fence validation**
   - **Given** the owner explicitly applies a pending proposal
   - **When** `applyApprovedTripChange(...)` runs
   - **Then** it authenticates the owner, locks the Trip Project, verifies ownership, status (`pending`), expiry, expected aggregate version, expected affected-item versions, and ordering/parent preconditions
   - **And** it applies every typed operation or none in one transaction; a partial write is impossible.

2. **Stale, expired, unauthorized, missing-item, or conflicting proposal applies nothing and safely requests refresh**
   - **Given** a proposal is stale, expired, unauthorized, references a missing item, or conflicts with a newer confirmed proposal
   - **When** application is attempted
   - **Then** no plan state is changed and the response safely requests refresh
   - **And** the proposal summary remains available without overwriting current owner data.

3. **Dismiss and expire are idempotent terminal actions that never mutate plan state**
   - **Given** an owner dismisses a pending proposal or its expiry elapses
   - **When** the corresponding command is invoked by a read, an application attempt, or a scheduled worker
   - **Then** it marks the proposal terminal idempotently without mutating plan state
   - **And** it records exactly one safe history row with actor and timestamp.

4. **Plan history shows safe structured effect, never raw model content**
   - **Given** a proposal is applied, dismissed, or expired
   - **When** the owner views plan history
   - **Then** it shows the status, safe operation summary, actor, timestamp, proposal ID, and affected item references
   - **And** it never exposes raw model prompts or responses.

## Scope And Boundaries

### In Scope

- Add the Chat/Trips-owned terminal proposal commands in `src/features/chat-trips/trip-change-proposals.ts`: `applyApprovedTripChange`, `dismissTripChangeProposal`, `expireTripChangeProposal`, plus the owner-scoped history read `listPlanHistoryForTripProject`. These are the only paths that mutate a proposal to a terminal status and the only path that applies typed operations to plan state.
- Refactor the existing internal plan-item primitives in `src/features/chat-trips/trip-projects.ts` so their core mutation logic runs inside a caller-supplied transaction. The public `createInternalTripPlanItem` / `updateInternalTripPlanItem` / `deleteInternalTripPlanItem` / `reorderInternalTripPlanItem` / `upsertInternalTripProjectConstraints` wrappers keep their current signatures (tests rely on them); new internal `*InTransaction(transaction, ...)` helpers are extracted so `applyApprovedTripChange` can apply every typed operation inside one locked transaction without re-locking or stale version errors. Add a new `changeInternalTripPlanItemStateInTransaction` helper for the state-only `change-item-state` operation so a state change does not require reconstructing the full `InternalPlanItemInput` shape.
- Implement the apply orchestrator: within one `getDb().transaction`, authenticate the owner, `SELECT ... FOR UPDATE` the Trip Project, verify `status = 'pending'` and `expiresAt > now` (when present), compare `tripProjects.aggregateVersion` to `expectedAggregateVersion`, load the current plan items + constraints, compare each affected existing item's `version` to `expectedItemVersions[itemId]`, re-validate `orderingPreconditions` against current state, then execute every typed operation through the `*InTransaction` helpers. All operations commit together or the whole transaction rolls back. On success: mark the proposal `applied` + set `terminalTimestamp`, write exactly one `trip_plan_change_history` row (`operationClass = 'apply'`, `actorClass = 'user'`), record an `audit_events` row (`operation = 'apply'`, `actorClass = 'user'`), and return the new aggregate version + applied proposal summary.
- Implement dismiss: `dismissTripChangeProposal({ tripProjectId, proposalId })` authenticates the owner, locks the proposal row `FOR UPDATE`, and if `status = 'pending'` sets `status = 'dismissed'` + `terminalTimestamp = now`, writes exactly one `trip_plan_change_history` row (`operationClass = 'dismiss'`, `actorClass = 'user'`, `actorUserId = session.userId`), and records an `audit_events` `dismiss` row. If the proposal is already terminal, the command is a no-op that returns the current summary without writing a second history row (idempotent). No plan state mutation.
- Implement expire: `expireTripChangeProposal({ tripProjectId, proposalId, now })` mirrors dismiss but sets `status = 'expired'`, writes the history row with `actorClass = 'system'`, `actorSystem = 'system-trip-planning'`, `actorUserId = null`, and records an `audit_events` `expire` row with `actorClass = 'system'`, `actorSystem = 'system-trip-planning'`. Idempotent on already-terminal rows. No plan state mutation. Owner-scope is enforced via the composite owner FK predicate; a cross-owner call returns `{ success: false, reason: "not_found" }` without leaking existence.
- Wire expire-on-read: `listPendingProposalsForTripProject` and `getProposalForOwnerReview` invoke `expireTripChangeProposal` for every returned pending proposal whose `expiresAt <= now` before returning the (now non-pending) list, so Trip Home focus and the workspace panel never treat an elapsed proposal as pending. Expire commands run in their own fenced transaction before the read; do not nest the read inside the expire transaction.
- Add a scheduled expiry worker `src/features/chat-trips/trip-proposal-expiry-worker.ts` exporting `processNextExpiredTripChangeProposal({ workerId, now?, db? })` and `runTripChangeProposalExpiryWorkerLoop({ once?, workerId?, pollIntervalMs?, signal? })`. It selects expired pending proposals `FOR UPDATE SKIP LOCKED` in bounded batches, invokes `expireTripChangeProposal` for each, and returns the count. Mirror the `src/features/knowledge/extraction-jobs.ts` loop shape (no lease/fencing token is needed because `expireTripChangeProposal` is idempotent and the `status = 'pending'` predicate + `FOR UPDATE` make duplicate workers safe).
- Add server actions `applyTripChangeProposalAction` and `dismissTripChangeProposalAction` in `src/features/chat-trips/actions.ts` mirroring the existing `deleteTripProjectAction` shape (typed result state, `redirect("/sign-in?next=/ai-ask")` on `unauthenticated`). The expire command is NOT a user action — it is invoked only by reads and the worker.
- Wire the apply/dismiss buttons in `src/features/ai/trip-proposal-review-card.tsx`: remove `aria-disabled` and `data-story="7.5"` hooks, accept optional `onApply`/`onDismiss`/`onRefresh` callback props, and invoke them on click. The card stays presentational and data-free; the composer owns the server-action calls, pending state, and reconciliation. Keep the expired-state gating (no apply button when expired; `refreshHint` shown). Add a visible `Làm mới đề xuất` affordance for the stale/conflict case (AC2) that calls `onRefresh`.
- Wire the composer handlers in `src/features/ai/ai-ask-composer.tsx`: `handleApplyProposal` calls `applyTripChangeProposalAction`, shows the "Applying proposal" pending state (disable duplicate actions, announce via `aria-live`), and on success reconciles via `router.refresh()` so the server-loaded workspace (Trip Home focus, timeline, pending proposals, plan history) reflects the new state. On `refresh_required` / `not_found` / `expired` failure, preserve the proposal summary, show the stale/conflict copy (`Kế hoạch đã thay đổi — làm mới đề xuất`), and offer `Làm mới đề xuất` which focuses the primary conversation composer for a fresh question (no automatic regeneration). `handleDismissProposal` mirrors this with the dismiss action. On terminal result, move keyboard focus back to the originating answer card heading (if the proposal came from the answer surface) or the Trip Home focus card (if the proposal came from the workspace panel) — 7.4 left this as a 7.5 hook.
- Add the plan history read + surface (AC4): `listPlanHistoryForTripProject(tripProjectId)` returns owner-scoped `TripPlanChangeHistoryRow[]` (`proposalId`, `operationClass`, `actorClass`, `actorSystem`, `createdAt`, `affectedItemReferences`, `safeBeforeAfterSummary`) ordered by `createdAt` descending, cross-owner returns `null`. Add a "Lịch sử kế hoạch" entry point in the workspace panel that opens the history as a sheet/dialog (mobile) or inline section (desktop); render each row with the Vietnamese operation label (`Áp dụng` / `Giữ kế hoạch` / `Đã hết hạn`), actor label (`Bạn` for `user`, `Hệ thống` for `system`), ICT timestamp, affected item labels, and the safe before/after summary. Never render raw model prompts/responses; the history row stores only the safe structured summary already derived in 7.4.
- Reconcile the answer-surface proposal card after a terminal action: when `applyTripChangeProposalAction` / `dismissTripChangeProposalAction` returns success, update the in-memory `message.proposal.status` so the card re-renders as terminal (no apply button, outcome announced), then `router.refresh()` to reconcile from persisted state. The `done` StreamEvent contract is unchanged; 7.5 only mutates proposal status client-side from the server-action result.
- Add focused regression coverage: pure unit tests for the apply orchestrator (mocked `*InTransaction` helpers) covering every operation kind, all-or-nothing rollback on the first failed operation, version-fence failures, expired/unauthorized/missing-item/conflict paths, and the cross-operation backup-cycle case deferred from 7.4; DB-backed tests for apply (real plan mutation, aggregate version advance, affected item version advance, history row, audit row, idempotent re-apply no-op), dismiss (idempotent, history row, no plan mutation), expire (idempotent, system actor, history row, no plan mutation), expire-on-read, cross-owner `not_found` without existence leakage; worker tests for `processNextExpiredTripChangeProposal` and `runTripChangeProposalExpiryWorkerLoop({ once: true })` including concurrent worker safety via `FOR UPDATE SKIP LOCKED`; shell tests for apply/dismiss button wiring, pending state, terminal focus return, refresh affordance on conflict, plan history rendering, and no raw model content.

### Explicitly Out Of Scope

- AI proposal auto-application, background proposal regeneration, scheduled regeneration, proposal notifications, and proposal expiry reminders — deferred; the scheduled worker only expires elapsed pending proposals, it never drafts new ones.
- Any change to the 7.4 proposal-drafting path (`trip-proposal-draft.ts`, `completeTripChangeProposalDraft`, `buildTripChangeProposalDraftMessages`, the `done` StreamEvent payload shape, or the `trip_proposal_draft` gateway/usage purpose). 7.5 only consumes persisted proposals and mutates their status/plan state.
- A new Drizzle migration. The `trip_plan_change_history` table schema, the `audit_events.operation` `apply | dismiss | expire` values, and the `audit_events.actorClass` / `actorSystem` columns were reserved in migration `0063` (7.4). 7.5 writes rows; it does not change schema. Run `pnpm db:generate` to confirm no drift.
- A manual plan-item/constraint editor, drag-and-drop reorder, inline state toggle, or any workspace control that mutates structured plan state outside `applyApprovedTripChange`. The primary conversation remains the sole plan-authoring surface; the timeline stays read-oriented.
- Maps, Google Maps, weather, live route/ETA, booking, availability, provider snapshots, current location, budget tracking, checklists, vault, notifications, sharing, collaboration, or location sharing.
- Changes to `formatTripProjectLabel`, `TripProjectInput`, legacy project metadata, `chat_context`, transcript extraction, answer-context behavior, retrieval/search, streaming/provenance persistence contracts, or the 7.4 proposal review card visual design (amber border, white bg, radius lg, no shadow/animation/saturated color).
- Knowledge-ingestion or community-knowledge changes; this story is Trip Planning only.

### Apply Contract (AD-30, AD-29, AD-6, NFR-11)

- AD-30 verbatim: "Only `applyApprovedTripChange(...)` in Chat/Trips may apply a proposal. In one transaction it authenticates the owner, locks the Trip Project, verifies proposal ownership/status/expiry, expected aggregate/item versions, and ordering/parent preconditions, applies all operations or none, records actor-correct audit/change-history rows, marks the proposal `applied`, and advances affected item/project versions. A conflict, expired proposal, missing item, or unauthorized request applies nothing and returns a safe refresh-required result."
- The single locked transaction is non-negotiable. The existing `*InternalTripPlanItem` public primitives each open their OWN transaction and would advance the aggregate version independently — calling them sequentially from `applyApprovedTripChange` would cause the second call's `expectedAggregateVersion` to be stale. The refactor in Task 1 (extract `*InTransaction` helpers) is the disaster-prevention step: the apply orchestrator threads ONE transaction through every helper so the aggregate version advances exactly once for the whole proposal and a failure in op 3 rolls back ops 1 and 2.
- Operation → helper mapping: `create-item` → `createTripPlanItemInTransaction`; `update-item` → merge `changes` onto the loaded current item to produce a full `InternalPlanItemInput`, then `updateTripPlanItemInTransaction`; `remove-item` → `deleteTripPlanItemInTransaction` (which already rejects when dependents/backups reference the item); `reorder-item` → derive `expectedChangedItemVersions` from the loaded scope and call `reorderTripPlanItemInTransaction`; `change-item-state` → `changeInternalTripPlanItemStateInTransaction` (new, avoids reconstructing the full item shape); `upsert-constraints` → `upsertInternalTripProjectConstraintsInTransaction` with `expectedConstraintsVersion` from the operation.
- Version fence: the proposal stores `expectedAggregateVersion` and `expectedItemVersions` (map itemId→version) captured at draft time (7.4). Apply MUST compare the current loaded versions to these fences before mutating. A mismatch means the plan changed after the proposal was drafted → `refresh_required`, apply nothing.
- Ordering preconditions: the proposal stores `orderingPreconditions` (jsonb, optional) for create/reorder operations. Apply MUST re-validate them against the current parent/ordinal state. The exact shape is whatever 7.4 captured; treat it as opaque structured data and re-check the precondition fields the validator recognizes (parentItemId, ordinal, expectedChangedItemVersions). If a precondition field is unrecognizable, fail closed → `refresh_required`.
- Cross-operation backup cycle (deferred from 7.4 second review finding): two `change-item-state` ops in one proposal (A→backup target B, B→backup target A) each validated independently against the pre-operation snapshot in 7.4, so a latent mutual-backup cycle can be persisted. 7.4 wrote no plan state; 7.5 `applyApprovedTripChange` MUST re-validate backup cycles against the post-apply state. Concretely: simulate the backup targets after all `change-item-state` ops apply, then run the `validatePlanReferencesRules` cycle check against the simulated set; if a cycle forms, return `refresh_required` and apply nothing.
- Actor-correct audit/history: `apply` and `dismiss` use `actorClass = 'user'`, `actorUserId = session.userId`. `expire` uses `actorClass = 'system'`, `actorSystem = 'system-trip-planning'`, `actorUserId = null`. ### Database And Concurrency Guardrails

- The apply transaction locks the Trip Project `SELECT ... FOR UPDATE` before any mutation. Every `*InTransaction` helper must use the SAME `transaction` object; do NOT call `getDb()` inside them. The `lockAggregate` helper already takes a transaction parameter — reuse it.
- Each `*InTransaction` helper advances `aggregateVersion` inside the shared transaction. The apply orchestrator must thread the UPDATED aggregate version from one op to the next (do not re-read it from the DB between ops — read it once at lock time, increment in-memory after each op, and pass the expected version to the next op's `expectedAggregateVersion`). The final `advanceAggregate` is effectively the sum of all ops' increments; verify the DB write happens once per op via the helpers (each helper writes `aggregateVersion = nextVersion`).
- Concurrent apply: two simultaneous `applyApprovedTripChange` calls for the same proposal — the first locks the proposal row `FOR UPDATE`, marks it `applied`, commits; the second's `FOR UPDATE` resolves to the now-terminal row, sees `status !== 'pending'`, and returns `{ success: false, reason: "not_found" }` (idempotent no-op, no second history row). This is the correct behavior.
- Concurrent apply vs. dismiss: same — the first to lock wins; the second sees a terminal status and returns a no-op success (dismiss) or `not_found` (apply). No partial writes.
- Worker vs. read expire: `expireTripChangeProposal` is idempotent; `FOR UPDATE SKIP LOCKED` in the worker plus the `status = 'pending'` guard in the command make concurrent expire safe. A row expired by the worker is absent from the next read's pending list.
- `pnpm lint`/`typecheck`/`build` must not require a live database. DB-backed tests run through the existing Vitest global setup (`tests/global-setup.ts`) that applies all Drizzle migrations. Mocked DB cannot prove owner scoping, cascade, or `FOR UPDATE` behavior — use the real PostgreSQL test database for the apply/dismiss/expire/worker DB-backed tests.

### Open Decisions Resolved For The Dev

1. **Single locked transaction for apply**: the apply orchestrator threads ONE `getDb().transaction` through every `*InTransaction` helper. The existing public `*InternalTripPlanItem` primitives cannot be called sequentially because each opens its own transaction and advances the aggregate version independently. The refactor in Task 1 is mandatory, not optional.
2. **State-only change primitive**: add `changeInternalTripPlanItemStateInTransaction` rather than reconstructing the full `InternalPlanItemInput` for a `change-item-state` operation. A state-only change must not touch label/notes/ordinal/plannedAt/transport/accommodation fields, and the dedicated primitive avoids the merge complexity and the risk of clobbering unchanged fields.
3. **No new migration**: `trip_plan_change_history` schema, `audit_events.operation` `apply | dismiss | expire`, and `audit_events.actorClass`/`actorSystem` columns were reserved in 7.4 migration `0063`. 7.5 writes rows only. Run `pnpm db:generate` to confirm no drift.
4. **System actor for expire**: use `actorClass = 'system'`, `actorSystem = 'system-trip-planning'`, `actorUserId = null` for the expire history + audit rows. For the `recordAuditEvent` `actor` parameter (which requires an `AuthenticatedSession`-shaped object), pass `{ userId: "system-trip-planning", email: "system-trip-planning@xuyenviet.invalid" }` — mirroring the `system-knowledge-pipeline` pattern in `src/features/knowledge/ingestion-pipeline.ts` (`systemActorId = "system-knowledge-pipeline"`, `systemActorEmail = "system-knowledge-pipeline@xuyenviet.invalid"`) and `src/features/knowledge/recommendations.ts` verbatim. Do not invent a new convention or extend `recordAuditEvent`.
5. **Refresh UX**: `Làm mới đề xuất` is an owner action that focuses the primary conversation composer for a fresh question. It does NOT auto-regenerate, does NOT call the AI gateway, and does NOT mutate plan state. Auto-regeneration is deferred.
6. **Reconciliation**: `router.refresh()` on apply/dismiss success re-derives the server-loaded workspace (Trip Home focus, timeline, pending proposals, plan history). The in-memory `message.proposal.status` is updated from the server-action result so the answer-surface card re-renders immediately. The `done` StreamEvent contract is unchanged.
7. **Expire call sites**: expire is invoked by (a) pending-proposal reads, (b) the scheduled worker, and (c) apply refuses an expired proposal WITHOUT calling expire (apply just returns `expired`; the next read will expire it). All three paths produce the same `expire` history row when they run. Apply writes NO history row on failure.
8. **Idempotency**: re-invoking dismiss/expire on an already-terminal proposal returns success WITHOUT writing a second history row. Re-invoking apply on an already-terminal proposal returns `{ success: false, reason: "not_found" }` (treat terminal as no-longer-applicable) WITHOUT writing a second history row.
9. **Plan history surface**: render as a sheet on mobile and a collapsible section on desktop (not a separate route). Coordinate with the existing answer-detail dialog and workspace sheet so only one `aria-modal="true"` dialog is open at a time (7.3 review fix to preserve).
