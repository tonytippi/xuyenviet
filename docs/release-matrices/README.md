# Schema Release Matrices

Store one reviewed JSON file for each durable-data or overlapping-runtime schema release in this directory. `20260728.1-to-20260729.1.json` is a versioned repository approval template for this overlap release, not evidence of a deployment or a credential. Its `.invalid` target must be replaced only in an operator-approved release input with the exact credential-free identity resolved from the live target; migration runs only when that live identity exactly matches the selected matrix. Supply a checked-in relative filename through `SCHEMA_RELEASE_MATRIX_PATH` to `pnpm db:migrate`. The command resolves the artifact by real path and rejects absolute paths, traversal, non-JSON files, and symlinks that escape this directory.

The file must validate through `parseSchemaReleaseMatrix` in `@xuyenviet/contracts`. It includes an `activeOwnerInventory`, an explicit attestation of every known active or deployable workload/capability owner. Entries have a stable ID, owner type/capability, old representation/schema, state, declaration, and deployment evidence. Capability owners also declare `runtimeWorkload`; their declaration must use that exact workload. This is a boundary, not external discovery: it supports legacy capability owners but cannot infer unknown owners. The checked-in template declares no admin runtime owner. Expand evidence and rollout apply only to active workload owners; contract retirement covers every attested owner.

Every phase retains declarations for `web`, `api`, `worker`, `admin`, and `migration`; those static schema declarations are not an active deployment inventory. Each phase validates its own ranges, including historical declarations. Only the active `migrate` declaration for `migration` must equal the current shared declaration. A destructive contract requires retirement evidence for every inventory entry and remains non-executable through `db:migrate`.

AD-32 traffic is structured as `{ writerOwnerId, dualWrite: false, readOnlyShadow }`; the selected writer must be an active inventory owner, dual writes are forbidden, and shadow mode is explicit. `rollback` is `{ legacyOwnerId, legacyBinaryRelease }`; it must select a compatible inventory owner and that owner's declared old deployment. It never consults the current global declaration as a substitute for the selected binary contract. Contract cleanup is a separate approved release after all owners are explicitly retired. Contract matrices remain parseable for review, but `db:migrate` accepts only `operation.phase=migrate` and cannot process contract cleanup. Runtime admission remains the existing static `schemaCompatibilityDeclarations`; a future version-changing release updates those shared declarations as part of deploying its new binary rather than relying on the matrix as automatic runtime authorization.
