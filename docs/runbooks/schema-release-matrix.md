# Schema Release Matrix Runbook

Every durable-data or overlapping-runtime release supplies a reviewed JSON matrix to `SCHEMA_RELEASE_MATRIX_PATH`. The matrix is release input, not deployed state; `release_schema_versions` remains the sole deployed-schema authority.

Required fields are validated by `parseSchemaReleaseMatrix` in `@xuyenviet/contracts`: a release ID, staging/production environment, durable/protected/operational class, exact credential-free resolved database identity, explicit approval reference, current and target versions, persistent-object interpretation, all five static workload ranges in expand/migrate/contract phases, and an explicitly attested inventory of active/deployable owners. Every owner has a stable ID, workload or capability type, explicit `reader` or `writer` role, effective `active` or `deployable` state, old representation/schema, declaration, and deployment evidence. Each capability owner declares its actual `runtimeWorkload`, and its declaration must match it. It cannot infer unknown external owners: operator attestation is the deliberate boundary. The checked-in template explicitly has no active/deployed admin runtime and models the API request-write capability separately from its reader workload. Expand evidence and rollout use every declared owner ID, including capability owners; contract cleanup requires retirement evidence for every active/deployable owner.

Run the migration only after the matrix declares a `migrate` operation and every active/deployable workload or capability owner is listed and evidenced before `verify-expand` and `migrate`. Each phase validates its own compatibility ranges and may document historical declarations; the active migration declaration alone must exactly equal the current shared deployed migration declaration. A durable rewrite is explicit: `operation.durableRewrite=true` requires the complete rewrite plan; it is forbidden otherwise. `migrationPlan` declares `forward_only` plus the ordered, exact pending Drizzle journal IDs and SHA-256 file digests (an empty list is an explicit no-op plan). Before DDL, the migration command compares that manifest to Drizzle's pending ledger using journal IDs and file hashes only; unmanaged or changed pending operations are rejected without parsing or executing their SQL. The job takes the advisory lock, verifies the exact target on the same PostgreSQL connection passed to Drizzle immediately before DDL, runs forward Drizzle migrations, then records the target version. A failure leaves the existing record unchanged.

AD-32 traffic declares one inventory `writerOwnerId`, `dualWrite: false`, and an explicit boolean `readOnlyShadow`; dual writes and unbound owners are rejected. Exactly one effective-active writer may cut over, and it must not run on the worker or migration workload. The selected ID must be `traffic.writerOwnerId`; a deployable-only writer or a reader cannot be selected. Rollback selects an effective-active, non-worker/non-migration, target-compatible legacy writer and its exact `legacyBinaryRelease`. Never run a down migration or delete expanded schema/data. `contract.oldOwners` must enumerate exactly every declared overlap owner and bind each to its declared old binary and schema version. Migration matrices may explicitly state `retired: false`; destructive contract artifacts require every bound owner to state `retired: true` with non-empty retirement evidence, plus cleanup constraints that retain expanded schema until retirement, prohibit destructive rollback, and keep cleanup forward-only. Contract matrices are valid review artifacts, but `db:migrate` accepts only `operation.phase=migrate` and rejects contract operations for execution. Contract cleanup belongs to a later, separately approved release; no destructive cleanup can be processed by `db:migrate`.

Each runtime receives `SCHEMA_RELEASE_PHASE_POLICY` only as a projection of an approved checked-in matrix. It must include `releaseId`, checked-in `matrixPath`, SHA-256 `matrixDigest`, exact target environment/identity class/resolved identity, phase, and phase workload declarations. Web, API, and worker reload the artifact and reject a projection that does not exactly match it. A missing projection admits only the exact static pre-overlap release record (`20260728.1`); any overlap target record without a valid projection fails closed.

`db:reset` and direct `db:seed` are only for explicitly confirmed local disposable targets with no runtime overlap. They require `APP_ENV=local`, `DB_RESET_DISPOSABLE_CONFIRMATION=confirm-disposable-reset`, and `DB_RESET_NO_RUNTIME_OVERLAP=confirm-no-runtime-overlap`; the confirmed resolved identity must have `127.0.0.1`, `::1`, or `local` socket host, exactly match the live target, and not resolve to a protected database name. Reset runs forward Drizzle, replaces the sole `release_schema_versions` record with the known migration target, then invokes the direct seed safety operation, which resolves and checks the identity again immediately before inserts; any migration, release-record, or seed preflight error prevents seeding. Neither command accepts release matrices as authorization, and `db:migrate` never accepts a clean-break disposition.
